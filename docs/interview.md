# cjp-cli-dev 面试问答手册

> 目标岗位：前端架构师 / 基础设施方向
> 本文档以模拟面试形式组织，涵盖项目架构设计、核心技术实现、工程化实践等方面。

---

## 一、项目整体介绍

### Q1：请简单介绍一下这个项目，它解决了什么问题？

**A：**

cjp-cli-dev 是我独立设计和开发的一套前端工程化脚手架，采用 Lerna monorepo 架构管理 20+ 个子包。它的核心目标是**标准化前端项目的全生命周期**——从项目初始化、代码规范配置、Git 工作流管理，到云构建和自动化发布。

它解决的核心痛点是：
1. **项目初始化效率低**：团队每次新建项目都要手动配置 ESLint、Husky、CommitLint 等，耗时且不统一。脚手架通过模板机制一键生成标准化项目。
2. **发布流程不规范**：手动构建、手动上传容易出错。通过云构建 + 自动化发布实现了标准化的 CI/CD 流程。
3. **工具碎片化**：Git Flow、版本管理、代码规范等工具散落各处，脚手架将它们整合为统一的命令行入口。

---

### Q2：为什么选择自己开发脚手架，而不是用 Yeoman、create-react-app 这类现成方案？

**A：**

现成方案的局限在于：

1. **扩展性不足**：Yeoman 主要聚焦项目初始化，对后续的发布、Git 工作流等缺乏支持。create-react-app 更是绑定 React 技术栈。
2. **定制成本高**：团队的构建发布流程、模板管理方式有特殊需求（比如我们需要支持云构建、组件库发布到私有 npm），改造现有工具的成本并不比自建低。
3. **学习和掌控**：自建脚手架让我对 CLI 工具链的底层原理有了深入理解——包括命令解析、进程管理、包管理机制等，这些是架构师必须掌握的基础设施能力。

当然，我在设计时也参考了 Vue CLI、create-react-app、Lerna 等优秀工具的架构思想，比如插件化设计、动态加载等。

## 二、架构设计

### Q3：请介绍一下项目的整体架构设计，为什么这样分层？

**A：**

项目采用了**四层架构**设计：

```
Core 层 → Commands 层 → Models 层 → Utils 层
```

- **Core 层**（`core/cli` + `core/exec`）：脚手架的入口和执行引擎。`cli` 负责命令注册、参数解析、环境检查；`exec` 负责动态加载命令包并在子进程中执行。
- **Commands 层**：具体命令的实现，如 init、publish、husky 等。每个命令都是独立的 npm 包。
- **Models 层**：可复用的功能模型，如 Command 基类、Package 包管理、Git 操作封装、CloudBuild 云构建通信。
- **Utils 层**：纯工具函数，如日志、路径处理、HTTP 请求等。

这样分层的原因：

1. **关注点分离**：每一层只关注自己的职责，比如 Core 层不关心具体命令怎么实现，Commands 层不关心包怎么下载。
2. **可独立发布**：每个包可以独立版本管理和发布，修改某个命令不需要升级整个脚手架。
3. **依赖方向单一**：上层依赖下层，下层不依赖上层，避免循环依赖。

### Q4：你选择 Lerna monorepo 的原因是什么？遇到了哪些问题？

**A：**

**选择原因：**

1. 项目有 20+ 个子包，彼此存在大量内部依赖。如果用多仓库管理，包之间的版本协调和联调会非常痛苦。
2. Lerna 提供了统一的版本管理（`lerna version`）和批量发布能力（`lerna publish`），非常适合这种场景。
3. monorepo 让代码变更的原子性更好——一个 PR 可以同时修改命令实现和底层模型，保证一致性。

**遇到的问题：**

最大的问题是 **`lerna bootstrap` 的软链失败**。在 Windows 环境下，`lerna bootstrap` 创建的 symlink 经常出问题，导致内部包之间的 `file:` 协议引用失败。

我的解决方案是写了一个自定义脚本 `scripts/install-deps.js`，替代 `lerna bootstrap`：
- 先清理所有子包的 `node_modules`
- 遍历四个包目录，逐个执行 `npm install`
- 最后在 `core/cli` 下执行 `npm link` 创建全局软链

这是一个务实的解决方案——没有花大量时间去解决 Lerna 本身的 bug，而是用一个简单脚本绕过了问题。

---

### Q5：如果让你重新设计，会做哪些改进？

**A：**

1. **包管理器升级**：考虑使用 pnpm workspace 替代 Lerna。pnpm 的硬链接机制天然解决了软链问题，且磁盘占用更小。Lerna 目前更多是作为发布工具使用。
2. **TypeScript 重构**：当前项目全部使用 CommonJS + JavaScript，类型安全性不足。TypeScript 可以在编译期捕获很多问题，尤其是在跨包调用时。
3. **插件化架构**：当前命令映射是硬编码在 `SETTINGS` 对象中的，可以改为插件注册机制，允许第三方开发者注册自定义命令。
4. **测试覆盖**：当前缺少系统性的单元测试和集成测试，需要补充。

## 三、核心技术实现

### Q6：命令的动态加载机制是怎么实现的？为什么不直接 require？

**A：**

这是脚手架最核心的设计之一。流程如下：

```
用户输入命令 → cli 解析命令名 → exec 查询 SETTINGS 映射表获取 npm 包名
→ 检查本地缓存是否存在该包 → 不存在则 npminstall 下载 / 存在则检查更新
→ 解析包的入口文件路径 → 在子进程中通过 node -e 执行
```

代码层面，`exec` 模块维护了一张映射表：

```javascript
const SETTINGS = {
  init: "@cjp-cli-dev/init",
  publish: "@cjp-cli-dev/publish",
  // ...
};
```

**不直接 require 的原因：**

1. **按需加载**：脚手架注册了 13 个命令，如果启动时全部 require，初始化会很慢。动态加载让用户只下载和执行用到的命令包。
2. **独立更新**：命令包发布新版本后，脚手架下次执行该命令时会自动检查更新，用户无需重装全局脚手架。
3. **开发调试**：通过 `--targetPath` 参数可以将命令指向本地路径，方便开发时调试，不需要每次都发布到 npm。

### Q7：为什么要在子进程中执行命令？直接在主进程执行有什么问题？

**A：**

在子进程中执行命令是一个经过深思熟虑的设计，主要出于三个考虑：

**1. 进程隔离与稳定性**

如果某个命令包有 bug 导致进程崩溃（比如内存泄漏、未处理的异常），如果在主进程执行，整个脚手架就会挂掉。子进程崩溃不影响主进程，主进程可以捕获退出码并给出友好提示。

**2. 性能优势**

`spawn` 创建的子进程可以充分利用多核 CPU。对于耗时操作（如 npm install、项目构建），子进程不会阻塞主进程的事件循环。

**3. 输出流管理**

通过 `stdio: 'inherit'` 配置，子进程的 stdout/stderr 直接继承主进程的终端，用户可以实时看到命令执行的输出和加载动画，体验与直接执行无异。

具体实现是将 `require` 调用转为字符串代码，通过 `node -e` 执行：

```javascript
const code = `require('${rootFile}').call(null, ${JSON.stringify(args)})`;
const child = spawn("node", ["-e", code], {
  cwd: process.cwd(),
  stdio: "inherit",
});
```

### Q8：Command 基类的设计体现了什么设计模式？为什么这样设计？

**A：**

Command 基类体现了**模板方法模式（Template Method Pattern）**。

基类定义了命令执行的骨架流程（生命周期）：

```
checkNodeVersion → initArgs → init → exec
```

其中 `checkNodeVersion` 和 `initArgs` 是基类的通用实现，而 `init` 和 `exec` 是抽象方法，强制子类实现：

```javascript
init() {
  throw new Error("子类中 init 方法必须实现！");
}
exec() {
  throw new Error("子类中 exec 方法必须实现！");
}
```

**这样设计的好处：**

1. **流程标准化**：所有命令都经过相同的前置检查（Node 版本、参数解析），避免每个命令各自实现导致遗漏。
2. **强制约束**：JavaScript 没有 abstract 关键字，通过基类方法抛出错误来模拟"接口契约"，如果子类忘了实现就会在运行时立即报错。
3. **复用性**：参数解析、版本检查等通用逻辑只写一次，子类通过 `this._args`、`this._cmd` 等属性直接使用。

这个设计也使用了 **Promise 链** 来管理异步生命周期，保证各步骤串行执行。

### Q9：Package 模型的缓存机制是怎么设计的？

**A：**

Package 模型是对 npm 包生命周期的完整封装，包括下载、缓存、更新、入口文件定位。

**缓存目录结构：**

```
~/.cjp-cli-dev/
├── dependencies/              # 命令包缓存
│   └── node_modules/
│       └── .store/            # 类似 pnpm 的扁平存储
│           └── @scope+pkg@version/
└── templates/                 # 模板包缓存
    └── node_modules/
```

**核心流程：**

1. **存在性检查**：通过 `getSpecificCacheFilePath` 拼接出精确的缓存路径，用 `pathExists` 检查包是否已下载。
2. **安装**：调用 `npminstall` 以编程方式安装包到指定目录，支持自定义 npm 源。
3. **更新**：调用 npm API 获取最新版本号，与当前缓存版本对比，有新版则重新安装。
4. **入口文件定位**：先用 `pkg-dir` 找到包的根目录，然后读取 `package.json` 的 `main` 字段，用 `format-path` 处理跨平台路径差异。

**支持自定义 npm 源**：所有涉及 npm 交互的地方都支持通过 `--registry` 参数指定源地址，兼容私有 npm 仓库。

### Q10：云构建是怎么实现的？为什么选择 WebSocket 而不是轮询？

**A：**

云构建的架构是：脚手架（客户端）通过 Socket.io 与后端构建服务（基于 Egg.js）建立长连接，由后端执行实际的构建任务。

**通信流程：**

```
脚手架客户端                         构建服务器
    │                                   │
    ├── socket.connect ──────────────→  │
    │                                   │
    ├── emit('build', 构建参数) ──────→ │ 开始构建
    │                                   │
    │  ←─── on('building', 日志) ─────  │ 实时推送日志
    │  ←─── on('building', 日志) ─────  │
    │  ←─── on('building', 日志) ─────  │
    │                                   │
    │  ←─── on('build_result') ───────  │ 构建完成
    │                                   │
    ├── disconnect ──────────────────→  │
```

**选择 WebSocket 而不是轮询的原因：**

1. **实时性**：构建过程会产生大量日志输出，用户期望实时看到编译进度。轮询有时间间隔，体验差。
2. **效率**：HTTP 轮询每次都要建立连接、发送完整请求头，对于频繁的日志推送来说开销太大。WebSocket 是持久连接，数据帧很轻量。
3. **双向通信**：除了服务器推送日志，客户端也可能需要发送中断信号，WebSocket 天然支持双向通信。

**容错设计：** 内置了 `doTimeout` 超时机制，如果指定时间内没有收到构建结果，会主动断开连接并提示用户，防止因网络问题导致命令无限等待。

## 四、工程化实践

### Q11：项目的日志系统是怎么设计的？如何支持 debug 模式？

**A：**

日志系统基于 `npmlog` 进行定制，增加了 `success`、`notice` 等自定义级别，并通过颜色区分。

**debug 模式的实现原理：**

1. Commander.js 监听 `--debug` 全局参数
2. 触发时将 `process.env.LOG_LEVEL` 设置为 `verbose`
3. `npmlog` 的 level 属性同步更新
4. 此后所有通过 `log.verbose()` 输出的调试信息都会显示

```javascript
program.on("option:debug", function () {
  const options = program.opts();
  process.env.LOG_LEVEL = options.debug ? "verbose" : "info";
  log.level = process.env.LOG_LEVEL;
});
```

**设计思路：** 正常使用时只显示关键信息（info 级别），调试时通过一个参数开关就能看到完整的执行过程，避免正常使用时信息过载。这是 CLI 工具的标准实践，npm 本身也是这么做的（`npm install --verbose`）。

### Q12：init 命令的模板机制是怎么设计的？如何支持不同类型的模板？

**A：**

模板机制支持两种类型：**标准模板**和**自定义模板**。

**标准模板（Normal）流程：**

```
从 npm 下载模板包 → 拷贝模板文件到当前目录 → EJS 渲染变量 → 执行安装命令 → 执行启动命令
```

EJS 渲染会遍历项目中所有文件（通过 glob 匹配），将 `<%= projectName %>` 之类的占位符替换为用户输入的实际值。

**自定义模板（Custom）流程：**

```
从 npm 下载模板包 → 找到模板包的入口文件 → 在子进程中执行入口文件，传入项目元数据
```

自定义模板的控制权完全交给模板开发者，他们可以在入口文件中实现任意逻辑，比如交互式选择功能模块、动态生成路由配置等。

**模板数据来源的双轨制：**

1. 优先读取本地配置文件 `~/.cjp-cli-dev/data/project.json`
2. 本地配置不存在时，通过 HTTP 接口从后端服务获取

这样设计的好处是：开发环境可以用本地配置快速调试，生产环境通过接口集中管理模板，新增模板无需更新脚手架。

**安全性：** 内置了命令白名单机制（`COMMAND_WHITELIST`），模板配置的 `installCommand` 和 `startCommand` 必须在白名单内才能执行，防止恶意模板注入危险命令。

### Q13：你是如何处理跨平台兼容性的？

**A：**

主要在三个方面做了跨平台处理：

**1. 路径兼容（format-path）**

Windows 使用反斜杠 `\`，macOS/Linux 使用正斜杠 `/`。`format-path` 工具统一将路径中的分隔符转换为 `/`，确保 `require` 和文件操作在所有平台一致。

**2. 进程创建（cross-spawn）**

Node.js 原生的 `child_process.spawn` 在 Windows 上对 `.cmd`、`.bat` 文件支持不好。项目使用 `cross-spawn` 库替代，它内部处理了 Windows 的 shell 转义、路径查找等差异。

**3. 用户主目录**

使用 `os.homedir()` 获取用户主目录，而不是硬编码 `~` 或 `%USERPROFILE%`，确保在所有平台都能正确定位配置和缓存目录。

### Q14：如何保证脚手架的版本更新体验？

**A：**

脚手架在每次启动时会执行**静默版本检查**：

1. 读取当前安装的版本号（`package.json` 中的 version）
2. 调用 npm Registry API 获取该包的所有版本号
3. 使用 `semver` 过滤出大于当前版本的最新版本
4. 如果有新版本，输出一行黄色提示，不中断当前操作

```
[warn] 更新提示 检测到脚手架有新版本：1.8.0，请运行 npm install -g @cjp-cli-dev/core 命令进行更新
```

**设计思路：** 只提示不强制，不打断用户的工作流。这是参考了 npm 自身的更新提示策略。检查过程是异步的，不会影响命令的启动速度。

## 五、高频追问

### Q15：如果脚手架要支持数千个团队使用，你会怎么扩展？

**A：**

1. **命令包的动态发现**：将 `SETTINGS` 映射表从硬编码改为从远程配置中心获取，不同团队可以注册不同的命令包。
2. **模板市场**：建立模板管理后台，支持团队自行上传和管理模板，通过标签和权限控制可见范围。
3. **插件生态**：定义标准的插件接口，允许第三方注册自定义命令、生命周期钩子、模板处理器等。
4. **遥测与统计**：收集命令使用频率、错误率等数据，指导功能迭代方向。
5. **灰度发布**：命令包版本支持灰度策略，先对部分团队推送新版本，验证稳定后全量发布。

最大的收获是**从使用者视角转变为设计者视角**。以前我用 Vue CLI、create-react-app 这些工具，只关心怎么用；做了这个项目后，我理解了：

### Q17：Lerna monorepo 的版本管理策略你是怎么决策的？Fixed 还是 Independent？

**A：**

项目使用的是 **Fixed 模式**（统一版本），当前版本号统一为 `1.7.5`。

选择 Fixed 模式的原因：
1. **简化发布**：所有包统一升版本，一次 `lerna publish` 全部发布，避免不同包版本号混乱。
2. **项目体量适中**：20+ 个包还在可管理范围内，Fixed 模式的"牵一发动全身"弊端不明显。
3. **内聚性强**：子包之间依赖紧密，核心包的变更往往确实需要下游包同步更新。

如果项目继续扩大（比如支持第三方插件），我会考虑切换到 **Independent 模式**，让各包独立版本管理，减少不必要的版本发布。

### Q18：你提到的"命令白名单"机制，具体是怎么考虑安全性的？

**A：**

模板的 `installCommand` 和 `startCommand` 是在服务端配置的，理论上可以配置任意 shell 命令。如果不做限制，恶意模板可以配置 `rm -rf /` 这样的危险命令。

白名单机制的实现：
1. 定义一个允许执行的命令列表（如 `npm`、`cnpm`、`yarn`、`pnpm`）
2. 执行前解析命令字符串，提取命令名与白名单比对
3. 不在白名单中的命令直接拒绝执行，并提示用户

```javascript
checkCommandInWhitelist(command) {
  if (!COMMAND_WHITELIST.includes(command)) {
    throw new Error(`命令 ${command} 不在白名单中，可能存在风险，已阻止程序运行。`);
  }
  return command;
}
```

这是**纵深防御**的一部分——即使模板数据源被污染，脚手架本身也有最后一道防线。

### Q19：root-check 是做什么的？为什么需要降级 root 权限？

**A：**

`root-check` 用于检测当前进程是否以 root（Linux/Mac）或管理员（Windows）权限运行，如果是则尝试降级为普通用户。

**需要降级的原因：**

1. **文件权限问题**：root 用户创建的文件默认权限很高，普通用户后续操作可能遇到 `EACCES` 权限错误。比如 root 用户下载的缓存包，切换到普通用户后就无法读取。
2. **安全性**：脚手架会执行 `npm install`、模板渲染等操作，如果以 root 权限运行且模板有恶意代码，破坏力更大。
3. **最小权限原则**：脚手架的所有操作都不需要 root 权限，按照安全最佳实践应该以最低必要权限运行。

这是 CLI 工具开发中容易忽视但非常重要的安全细节。
